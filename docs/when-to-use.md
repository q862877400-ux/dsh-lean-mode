# lean 模式：解决什么问题、该怎么用

> 全部数字都是本机实测。口径写在各表下面。

---

## 一、它解决的是什么

**一句话**：

> **当工具多到上下文装不下时，把工具面压下来 —— 砍掉参数细节、只留顶层契约，
> 并用一份极短的名字索引保住「我知道有哪些工具可用」。**
> **它买的是上下文，付的是准确率。**

### 它**能**解决

| 能 | 依据（实测） |
|---|---|
| ★ **上下文装不下时把工具面压下来** | 731 个**肥** schema：275,020 → **67,911** token（**0.247×**）；官方 72 个**常规** schema：通道 **19,886 → 12,318 B（0.619×）** |
| ★ **对抗注意力漂移**：几百个工具里只用记得住的那几个 | 名字索引把**全部**工具列出来（**15.5 B/工具**；731 个 = **11.3 KB，占 65536 指令预算 18%**） |

### 它**不能**解决

| 不能 | 依据 |
|---|---|
| ❌ **不可能「不丢信息还大幅省」** | 参数信息必须抵达模型 ⇒ 无论 JSON Schema / TS 类型 / 任何编码，都是 **O(N)**。PTC 的 `renderToolsSdk()` = **719 B/工具**，只比 JSON Schema(814) 省 **11.7%** |
| ❌ **不提升准确率** | 端到端可调用 **89.9%（lean） vs 95.0%（native）** —— **低 5 个点** |
| ❌ **不是通用省钱手段** | 43 个普通工具：首轮 input **15,831 → 13,240（仅 −16.4%）**；schema 越瘦越不划算，极瘦时反而更贵 |
| ❌ **不解决「该不该挂这么多工具」** | 那是**按需挂载 preset** 的事（能减 N 就先减 N） |

## 二、该不该用（三问）

```
① 工具通道现在占多少上下文？装得下吗？
     装得下  ⇒ ★ 别用 lean。用 native，或 index 档（全量 + 名字索引）
     装不下  ⇒ 问 ②

② N 能不能减？（把工具按需挂进不同的 preset）
     能   ⇒ ★ 先减 N，lean 只是兜底
     不能 ⇒ 问 ③

③ 调错的代价 vs 上下文的代价，哪个大？
     调错贵   ⇒ 宁可装不下也别砍 → index 档
     上下文贵 ⇒ lean（承认 −5 个点）
```

### 三档定位

| 档 | 配置 | 通道 | 指令区索引 | 信息 | 用在哪 |
|---|---|---|---|---|---|
| **native** | 不装 | 全量 | 无 | 全量 | 工具少 |
| ★★ **index** | `shape: false` | ★ **全量** | 15.5 B/工具 | ★ **全量 + 全可见** | ★ **工具多、要准**（多花索引那点） |
| ★ **lean** | 默认（`shape: true`） | 浅 | 15.5 B/工具 | ★ 丢嵌套/数组/枚举>12/默认值/描述第二句 | ★ **上下文装不下**时 |

## 三、怎么用（配置）

```yaml
config:
  presets: [lean]      # 只对点名的 preset 生效；不写 = 所有会话
  shape: true          # ★ 有代价的那一项：把参数压成顶层契约
  catalog: true        # 名字索引（默认）。15.5 B/工具
  # catalog: 'full'    # ★ 不推荐：带形状+一句描述 = 138 B/工具 ⇒ 731 个 = 101 KB，爆指令预算
```

要**只要可见性、不丢信息**（index 档）：`shape: false, catalog: true`。

## 四、别怎么用（四条弯路，我都走过）

| ❌ 弯路 | 为什么错 |
|---|---|
| **为了省 token 而用 lean** | 省是**副产品**。硬指标是**调用准确率**。 |
| **为了让 lean 省得多而把 schema 写肥** | ★ **本末倒置**。该写的是「准」（该有的信息一个不少、冗余一个不多）。 |
| **把目录写肥**（每条带实参形状 + 一句描述） | 138 B/工具 ⇒ 731 个 = **101 KB = 指令预算的 155%** ⇒ **会把 AGENTS.md 撑到被截断**。★ 目录进的是**指令区**，而**指令区越短遵循度越好**。 |
| **以为它提升准确率 / 拿 PTC 背书** | 实测**降 5 个点**；PTC 解决的是**批量调用**，不是「工具太多」，它的 SDK 段**同样是 O(N)**。 |

---

## 五、一句话决策

```
工具少            → native
工具多、要准      → index（全量 schema + 名字索引，多花 ~11 KB/731 个）
工具多、上下文紧  → lean（承认准确率下降）
工具多、能减 N    → ★ 先减 N（按需挂载 preset），以上都不必
```
